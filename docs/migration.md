# Migrating a 2.x workspace to 3.0

*What `kit/setup.sh migrate` moves, how to run it, and the map file that carries a workspace's own
moves.*

---

## What it does

In a 2.x workspace the kit sits at another path (often `templates/agentic-workspace`), its plugins are
copied into `.claude/plugins/`, the skills it generated sit in `skills/`, and copies of its docs,
rituals and templates sit beside the team's own files. In 3.0 the kit is a submodule at `kit/`, read in
place, and the workspace holds only what is the team's.

The migration makes that move in the same repository, keeping its history and its remote. Every action
prints one line before it happens, starting with its verb:

| Verb | Meaning |
|---|---|
| `move` | A path moves, with `git mv` when it is tracked and a plain move otherwise |
| `retire` | A path leaves the index (when tracked) and moves under `_delete/`, which is gitignored |
| `edit` | A file changes, named with the line where there is one |
| `config` | A git setting is written, in `.gitmodules` or in the repository's own config |
| `run` | Another kit script, or a git command, runs |
| `note` | Something to look at; nothing is done |
| `skip` | A step that is already done here, or does not apply |

The steps, in order:

| Step | What happens |
|---|---|
| M0 | A kit checkout with a `.git` folder of its own is absorbed into the workspace's `.git/modules` |
| M0b | Gitlinks with no `.gitmodules` entry are resolved by the map's `submodule-register` or `untrack` lines |
| M1 | The kit checkout moves to `kit/` with `git mv`. The submodule keeps its name, and `.gitmodules` gains `branch = main` |
| M2 | A vendored install with no kit submodule gets one at `kit/` |
| M3 | `.claude/settings.json` names `kit` as the plugin marketplace. Nothing else in that file changes |
| M4 | `.claude/plugins/` is retired |
| M5 | Skills in `skills/` (and copies in `.claude/skills/`) that carry the line `Generated by install.sh from plugins/` are retired. Every other skill is the team's own and stays |
| M6 | Copies of the kit's docs, rituals, templates and pilot files that match the kit's file byte for byte are retired, and `.claude/projects.md` and `.claude/closeout.md` point at `kit/<path>`. A copy that differs is the team's now; a note says so |
| M7 | References to the old kit path in tracked text files now name `kit/`. Dated records (`logs/`, `projects/_done/`, any file named for decisions, and what the map's `historical` lines name) keep their wording, with a note. An occurrence inside a `keep` literal stays as written |
| M8 | The git hooks are set (`kit/lib/setup/gitconfig.sh --hooks`). A hooks path already in effect is kept as `aw.chainHooksPath`, so a hook of your own still runs after the kit's |
| M9 | The submodule settings are set (`kit/lib/setup/gitconfig.sh --submodules`) |
| M10 | Lines of `kit/templates/workspace.gitignore` that are missing are added to `.gitignore` |
| M11 | When `.claude/projects.md` keeps finished projects in a folder of their own, each moves to `projects/_done/<slug>/`, and the Done setting and the register's links follow. An ignored folder gets an ignore line at its new place before it moves |
| M12 | When paused projects sit in a folder of their own, the Paused setting says they stay in place from now on. Nothing moves; a note counts them |
| M13 | `CLAUDE.md` gains the kit import on line 1 and a fallback line under it |
| M14 | With `--developer`, `kit/` is put on `main` for kit development |
| M15 | `kit/install.sh` creates the files the team owns from 3.0 on, such as `.claude/workspace.md` and the ledger `.claude/kit-templates.lock` |
| M16 | The map file's lines run, in order |
| M17 | The skills bridge runs, when there is a `skills/` or `.claude/skills/` folder |
| M18 | Anything that still names a path this run moved gets a note, outside dated records and `keep` literals |

Three things hold throughout:

- **Nothing is deleted.** What leaves the workspace waits in `_delete/`, and a person deletes it.
- **Nothing is committed.** The run ends with a commit plan: the moves it staged, then a `git add` line
  that names each path.
- **Opaque files are left alone.** `AGENTS.md` and `copilot-instructions.md` (or the list in
  `AW_OPAQUE_PATHS`) are never opened, changed or moved, and every scan leaves them out.

## When to reach for it

When a workspace was set up with a 2.x kit. `kit/setup.sh update` recognises the 2.x layout and hands
over to the migration's dry run by itself.

## Running it

A dry run first. It prints the same lines as the real run, each starting with `would`, and changes
nothing in the workspace:

```
templates/agentic-workspace/setup.sh migrate --dry-run --map ../field-study-migration.map
```

Then the real run:

```
templates/agentic-workspace/setup.sh migrate --map ../field-study-migration.map
```

The kit checkout at the old path has to be the 3.0 kit already (it holds `CLAUDE.kit.md`). When it
is not, `--kit-from URL` fetches the kit into that checkout first, at `main` or at `--kit-ref REF`.
This part runs in a dry run too, since the rest of the dry run reads the kit it migrates to. It also
brings in the kit for a fresh clone whose submodule is not populated yet.

| Option | Effect |
|---|---|
| `--dry-run` | Print what would happen, and change nothing |
| `--map FILE` | The workspace's own moves (below). The file sits outside `kit/`, which is public |
| `--kit-from URL`, `--kit-ref REF` | Bring the kit checkout to REF from URL before anything else (also `AW_KIT_URL`) |
| `--allow-staged` | Run although the index has staged changes. A rerun does not need it for the changes an earlier run staged |
| `--developer` | Put `kit/` on `main`, set to rebase, for developing the kit in place |
| `--confirm-private-origin` | Record `origin` under Private remotes in `.claude/workspace.md`, confirmed by you (`via person`) |

A run that stops partway exits 3 and names the step; a second run picks up where it stopped. A second
run after a finished one prints only `skip` lines.

Exit codes: `0` finished, or a dry run; `1` a precondition (not a repository, staged changes, no 3.0
kit to migrate to); `2` a usage error or a malformed map; `3` stopped at a step.

## The map file

A map holds the moves that belong to one workspace: folders renamed, material taken out of the
repository, references rewritten. It names the workspace's folders, so it is kept with the workspace
or outside it, never inside `kit/`.

- One action per line. Blank lines, and lines starting with `#`, are ignored.
- Fields are separated by tabs. A line with no tab is split on spaces, so simple paths need no tabs.
- Paths are relative to the workspace root, with no leading `/` and no `..`. A line that breaks these
  rules, uses an unknown verb, or names an opaque file is malformed: the run stops with exit 2 before
  anything moves.
- Lines run in order, after the kit's own steps (M16). The `submodule-register` and `untrack` lines
  that resolve a gitlink with no `.gitmodules` entry run first, at M0b.
- A destination that exists already is skipped, and so is a source that is not there, which lets the
  same map run on a clone where ignored material is missing.

| Verb | Fields | What it does |
|---|---|---|
| `git-mv` | `<from> <to>` | `git mv` of a tracked file or folder, creating the parents of `<to>`. The `.gitignore` lines that name `<from>` are listed, each with the `gitignore-rewrite` line that would carry it over |
| `submodule-mv` | `<from> <to>` | The same for a submodule; `<from>` is a gitlink |
| `mv` | `<from> <to>` | A plain move, for untracked or ignored material. When `<to>` is not ignored as `<from>` was, a note says its files now show as untracked |
| `retire` | `<path>` | Out of the index when tracked, then moved under `_delete/` |
| `untrack` | `<path>` | `git rm -r --cached` (the files stay on disk), then `/<path>` added to `.gitignore` |
| `gitignore-add` | `<pattern>` | Added to `.gitignore` when it is not there |
| `gitignore-rewrite` | `<from> <to>` | Each `.gitignore` line that starts with `<from>` (or `!<from>`, or either with a leading `/`) starts with `<to>` instead |
| `rewrite` | `<from> <to> [<glob>…]` | In tracked text files, `<from>` becomes `<to>` wherever it follows the start of a line, a space, `(`, `[`, a backtick, a quote or `/`. With globs, only in the files they match; without, outside `kit/`, opaque files and dated records. `<from>` is at least three characters. Text already rewritten is left as it is |
| `keep` | `<literal>` | No `rewrite`, and not M7, touches an occurrence of this text: a path that shares a prefix but means something else |
| `historical` | `<glob>` | The files the glob matches, relative to the workspace root, are dated records: M7, every `rewrite` (one with globs included) and M18 leave them as written. `*` crosses folders, and a glob that names a folder covers what it holds. For handoff notes, specs and other dated material outside `logs/`. It holds from the start of the run, wherever it sits in the map. The run lists the files under the line. M7 runs before the map's moves and M18 after them, so a record the map moves is named at both paths |
| `submodule-register` | `<path> <url> [<branch>]` | Writes the `.gitmodules` entry for a gitlink that has none, so it becomes a registered submodule |
| `header` | `<project folder> Versioned=<value> [Sensitivity=<value>]` | Writes the versioning lines of `<project folder>/README.md`: `Versioned:` is `workspace`, `own-repo` or `untracked`, and `Sensitivity:` is `normal` or `sensitive`. A line already there with another value is rewritten; a missing one is written as `- **Versioned:** <value>` directly under the title, or beside the other line. A line that already says the value is skipped. When the folder is `untracked` and `.gitignore` does not list it yet, a note gives the `gitignore-add` line that would |
| `note` | `<text…>` | Printed with the run; nothing is done |
| `private-term` | `<regex>` | Adds the term to `.claude/private-terms.local` (gitignored, never in `kit/`). The kit's hooks refuse it, whole word in any case, in any line, path or message committed or pushed to the kit. For client, product and people names; the output names the map line, not the term |

Order matters where material has to stay out of the repository. Put the ignore line before the move
that brings the material under a tracked folder, as in the example below.

## An example map

A team's workspace, kept at `field-study-migration.map` beside the workspace:

```
# The field-study team's own moves for the 3.0 layout.

# Paused projects sat in on-hold/; they come back under projects/. The private folder of
# vendor-review stays out of the repository, so its ignore line comes first.
gitignore-add	/projects/vendor-review/private/
mv	on-hold/vendor-review	projects/vendor-review
gitignore-rewrite	on-hold/	projects/

# A standalone repository inside the workspace becomes a registered submodule.
submodule-register	projects/survey-tool	https://github.com/example-org/survey-tool.git	main

# The published site, its own repository, moves under projects/.
submodule-mv	site	projects/site

# Reference notes move under memory/, and the references follow. A vendor's notes folder shares the
# name and keeps its path.
git-mv	notes	memory/notes
keep	vendor/notes/README.md
rewrite	notes/	memory/notes/

# Handoff notes are dated: they keep the paths they were written with.
historical	projects/*/handoff/*

# The intake form holds participants' contact details: it stays on this machine and leaves the
# repository. Earlier commits still hold it; what to do about that is the team's call.
untrack	projects/field-study/intake.md

# A paused grant application holds a funder's budget figures. It comes back under projects/ kept
# out of the repository, and its README says so.
gitignore-add	/projects/grant-application/
mv	on-hold/grant-application	projects/grant-application
header	projects/grant-application	Versioned=untracked	Sensitivity=sensitive

# An old draft, set aside for a person to delete.
retire	docs/old-onboarding.md

note	Ask Priya Shah whether vendor-review is sensitive before running /projects:hold on it.
```

## What it leaves alone

- The files inside `kit/`: the migration reads the kit, moves its checkout and, with `--kit-from` or
  `--developer`, changes which commit or branch it has out, and edits none of its files.
- Opaque files, and any map line that names one.
- A skill without the generator's line, a copy of a kit file that differs from the kit's, and a
  `CLAUDE.md` of the team's own below the two lines it adds.
- The history. `untrack` and `retire` change what is tracked from now on; earlier commits still hold
  what they held.
- Other submodules, such as a store of scheduled tasks or a skill kept as its own repository, beyond
  what `kit/lib/setup/gitconfig.sh` sets for projects.

## Common questions

**Does the dry run change the kit checkout?** No. With `--kit-from` it asks the remote which commit
it would fetch (`git ls-remote`, which writes nothing) and prints the lines the real run would print:
`init`, `config` and `update` for an unpopulated submodule, then the fetch and the checkout, or a skip
when the kit is there already. It reads the kit checkout when that is 3.0 already, and otherwise the
kit the script itself came from. A step handed to another script (the hooks, the submodule settings,
developer mode, the engine) prints what that script would set or create, indented under its line.

**The run stopped partway.** Fix what it names and run the same command again. It resumes where it
stopped, and its commit plan and its list of leftover references cover the earlier run too: both are
kept in `.git/aw-migrate-state` until a run finishes.

**`CLAUDE.md` was the 2.x one-line shim (`@AGENTS.md`).** The migration adds the kit import above it,
so the kit's standards load and the team's still load through `AGENTS.md`. Moving the team's sections
into `CLAUDE.md`, in the shape of `kit/templates/workspace/CLAUDE.md`, is left to the team; a note
says so. Until then the kit-generic sections of the old `AGENTS.md` load twice.

**A note says a copy of a kit file differs.** That copy is the team's now, and the conventions keep
pointing at it. The note gives the `rewrite` line that would point them at the kit's copy instead.

**The run stopped at a gitlink with no `.gitmodules` entry.** Add `submodule-register <path> <url>` to
the map to make it a submodule, or `untrack <path>` to keep it as a local repository the workspace
ignores, and run again.

**What goes in the commit?** The plan at the end: the moves and removals the run staged, then one `git
add` line naming every path it created or changed. A path the run's own `.gitignore` lines keep out,
such as an untracked project, is left off that line, in the dry run as in the real one, since `git add`
refuses a line that names an ignored path. The commit is yours to make.

**The kit had a `.git` folder of its own.** M0 absorbs it into the workspace's `.git/modules/<submodule
name>`, and M8 then points the kit's hooks there, even when they were set before. The dry run names the
kit's hooks path as it will be after that move, not the folder inside the old checkout.

## Pointing Claude Code at `kit/`

The workspace's `.claude/settings.json` names the marketplace at `kit` once M3 has run. A person who
added the kit's marketplace by hand in 2.x, from the old path, also has a user-level entry of the same
name that still points there, and `/plugin` shows that path. Re-point the user entry alone, after the
migration's commit. `claude plugin marketplace remove` without `--scope` removes the marketplace from
every scope, the workspace's settings included: it takes out `extraKnownMarketplaces.agentic-workspace`
and the three `…@agentic-workspace` entries in `enabledPlugins`, and uninstalls the plugins. With
Claude Code closed, run these one at a time from the workspace:

```
claude plugin marketplace remove --scope user agentic-workspace
claude plugin marketplace add --scope user ~/field-workspace/kit
claude plugin install closeout@agentic-workspace
claude plugin install projects@agentic-workspace
claude plugin install workspace@agentic-workspace
git diff -- .claude/settings.json
```

The last command prints nothing when the workspace's settings are as committed. If it prints a change,
put the file back:

```
git checkout -- .claude/settings.json
```

Then start Claude Code in the workspace and check `/plugin`.

## It's working if

- The dry run and the real run print the same action lines, apart from `would`.
- A second run prints only `skip` lines.
- `kit/setup.sh` afterwards reports the hooks active and the kit at `kit/`, and `/plugin` in Claude
  Code shows `agentic-workspace` at the workspace's `kit/`.
- Everything that left the workspace is under `_delete/`.
